# راهنمای پروژه IMED Manager

سامانهٔ **IMED Manager** برای مدیریت اسناد توزیع، ورود جزئیات فاکتورهای سپیدار، تطبیق چندفاکتوری، مدیریت Snapshot انبار مجازی IMED و آماده‌سازی خروجی XML یا اسکریپت JavaScript جهت ثبت سند در IMED طراحی شده است.

> **وضعیت مستند:** نسخهٔ رابط کاربری 0.31.1 (۲۷ نوامبر ۲۰۲۶). ثبت عملیاتی در سامانهٔ واقعی IMED و سازگاری نهایی XML هنوز تأیید نشده است. این README راهنمای پروژه است، نه گواه آماده‌بودن Production.

## امکانات اصلی

- **داشبورد:** نمایش آمار اسناد، ردیف‌های سپیدار و وضعیت تطبیق.
- **ورود اطلاعات:** دریافت Excel/CSV، انتخاب شیت، مپینگ ستون‌ها، پیش‌نمایش و ثبت در پایگاه دادهٔ مرورگر.
- **اسناد توزیع و فاکتورهای سپیدار:** جست‌وجو، مشاهده و خروجی CSV.
- **تطبیق و ردیابی:** اتصال یک سند توزیع به چند ردیف فاکتور با تاریخ، مقدار و قیمت مستقل؛ پیشنهاد تطبیق با IRC و نام کالا.
- **جدول جامع:** محاسبهٔ تطبیق پیشنهادی و نمایش موارد ناقص یا نیازمند بررسی.
- **انبار مجازی:** دریافت Snapshot موجودی از IMED از طریق فایل یا اسکریپت قابل اجرا در صفحهٔ IMED؛ جست‌وجوی InventoryID و IRC.
- **تولید XML:** اعتبارسنجی اطلاعات و تولید ساختار `QuotaList/Quota` برای ردیف‌های معتبر.
- **اسکریپت ثبت IMED:** تولید JavaScript برای کمک به تکمیل فرم؛ اجرای آن در دامنهٔ IMED و تأیید نهایی با کاربر است.
- **تنظیمات و پشتیبان‌گیری:** خروجی SQLite و بازیابی داده‌های محلی.

## گردش کار پیشنهادی

1. برنامه را باز کنید و از داده‌های موجود **نسخهٔ پشتیبان SQLite** بگیرید.
2. از بخش «ورود اطلاعات»، فایل‌های IMED و سپیدار را انتخاب کنید؛ ستون‌ها و پیش‌نمایش را بررسی و سپس تأیید کنید.
3. در «تطبیق و ردیابی» یا «جدول جامع»، ردیف‌های فاکتور را به اسناد توزیع مرتبط کنید.
4. از سامانهٔ IMED، Snapshot تازهٔ انبار مجازی تهیه و در برنامه وارد کنید.
5. برای سند منتخب، `InventoryID`، `TypeID` و `ReceiverCode` را بررسی کنید.
6. در بخش «تولید XML» اعتبارسنجی را اجرا و خروجی را بازبینی کنید؛ یا از بخش «اسکریپت ثبت IMED» کد آماده‌سازی فرم را بگیرید.
7. نتیجه را در محیط واقعی IMED **با نظارت کاربر** بررسی کنید؛ ارسال و تأیید نهایی را دستی انجام دهید.

## قواعد کسب‌وکار مورد توافق

- تطبیق یا تخصیص **کمتر از مقدار سند** مجاز است؛ خروجی باید مقدار واقعی را نشان دهد و دربارهٔ کسری هشدار بدهد. تخصیص بیش از مقدار سند رد می‌شود.
- اگر نوع دریافت‌کننده یا توزیع قابل تشخیص نباشد، `TypeID = 2` به‌عنوان مقدار پیش‌فرض پذیرفته است.
- اطلاعات ضروری نامعتبر نباید بی‌صدا از XML حذف شوند؛ ساخت خروجی در این حالت متوقف می‌شود.
- تأیید نهایی ثبت در IMED خودکار نیست.

## ساختار فنی و فایل‌های مهم

| مسیر | کاربرد |
|---|---|
| `index.html` | پوسته و بخش‌های رابط فارسی |
| `assets/js/app.js` | منطق اصلی برنامه و گردش کار سمت مرورگر |
| `assets/css/styles.css` | ظاهر رابط |
| `cloudflare/worker.js` | API مربوط به Cloudflare Worker |
| `tampermonkey/IMED_Grok_Tampermonkey.user.js` | اسکریپت کمکی مستقل؛ داده‌های آن لزوماً زنده نیست |

پایگاه دادهٔ اصلی برنامه **SQLite محلی در مرورگر** است و ذخیره‌سازی مرورگر نیز در گردش کار استفاده می‌شود. Cloudflare Worker/D1/R2 اجزای مرتبط با امکانات ابری هستند؛ وجود کد به معنی Deploy یا Migration موفق Production نیست.

## اجرای پروژه و آزمون‌های پایه

رابط برنامه از `index.html` شروع می‌شود. برای اجرای محلی، پروژه را با یک HTTP static server مناسب باز کنید؛ در صورت استفاده از قابلیت‌های مرورگر و کتابخانه‌های خارجی، دسترسی و سیاست‌های امنیتی مرورگر را در نظر بگیرید.

دستورهای بررسی که در گزارش ممیزی پروژه ثبت شده‌اند:

```bash
node --check assets/js/app.js
node --check tampermonkey/IMED_Grok_Tampermonkey.user.js
node --input-type=module --check < cloudflare/worker.js
node tests/project-contract.test.mjs
```

این آزمون‌ها جایگزین تست واقعی مرورگر، import فایل‌های نمونه، restore SQLite یا تست ثبت در IMED نیستند.

## Branchها و انتشار

- `main`: مرجع Production و مبنای انتشار.
- `development`: محیط توسعهٔ جداگانه که ممکن است تنظیمات متفاوت داشته باشد.
- تغییرات جدید بهتر است در Feature Branch ساخته، بررسی و سپس با PR به `main` منتقل شوند.
- تاریخچهٔ تغییرات را در `CHANGELOG.md` و قواعد نسخه‌گذاری را در `VERSIONING.md` دنبال کنید.

## محدودیت‌ها و کارهای باقی‌مانده

1. **XML:** مقایسهٔ ساختار و فیلدها با نمونهٔ رسمی معتبر IMED یا تست در محیط واقعی.
2. **فرم ثبت:** تأیید Selectorها و پرشدن جدول مرحلهٔ دوم در DOM زندهٔ `register.imed.ir`؛ ثبت نهایی همچنان دستی.
3. **Tampermonkey:** داده‌های نسخهٔ مستقل ثابت‌اند و به‌طور زنده از SQLite برنامه استخراج نمی‌شوند.
4. **Cloudflare:** پیش از هر Migration واقعی D1، تهیهٔ Backup و بررسی Schema و Deployment ضروری است.
5. **امنیت:** کلید مشترک API در localStorage جایگزین احراز هویت فردی برای عرضهٔ عمومی نیست.
6. **End-to-end:** تست واقعی import Excel، تخصیص چندفاکتوری، بازیابی SQLite و مرورگر Android/Chrome باقی است.
7. **Saba:** پوشهٔ `saba/` نمونهٔ مستقل آزمایشی است و بدون احراز هویت مدیر، پایگاه دادهٔ مشترک و پرداخت آنلاین برای فروش واقعی آماده نیست.
